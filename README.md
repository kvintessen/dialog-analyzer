# Dialog Analyzer

Внутренний сервис для анализа диалогов менеджеров с клиентами: авторизация,
просмотр переписок и автоматический поиск потенциально важных ситуаций
(долгий ответ, клиент замолчал, возражение, затянутый диалог без продажи) по
настраиваемым правилам.

Стек: PHP 8.3 / Laravel 13, Inertia v2 + Vue 3 (Composition API, без TS),
shadcn-vue, PostgreSQL, Docker Compose.

`make install`, `make key`, `make migrate`, `make npm-build` — полный список

рабочие значения по умолчанию, отдельно настраивать не нужно. `docker compose up`
(и, соответственно, `make up`/`make setup`) поднимает и `queue-worker`
(`php artisan queue:work`) — без него автоматический анализ по новым
сообщениям не запускается.

Тестовые пользователи (пароль у всех `password`):

| Email | Роль в датасете |
|---|---|

## Модель данных

```
users 1───* dialogs 1───* messages
                 │
                 └──────* analysis_events *───1 analysis_rules
```

- **dialogs** — `manager_id`, `client_name`, `result` (`purchased` /
  `not_purchased` / `undecided`). Даты начала/последнего сообщения не
  хранятся отдельно — берутся из `messages` через `withMax`, чтобы не
  дублировать данные, восстановимые из переписки.
- **messages** — `sender` (`manager` / `client`), `body`, `sent_at`
  (бизнес-время, отдельно от служебного `created_at`). Индекс
  `(dialog_id, sent_at)` — под сортировку и правила, работающие с
  последовательностью сообщений.
- **analysis_rules** — каталог правил: `key` (связывает строку с классом),
  `name`, `description`, `severity`, `enabled`, `config` (jsonb — параметры
  правила, например порог в минутах). Редактируется в разделе «Правила
  анализа» — пороги, критичность и включение/выключение меняются без
  деплоя.
- **analysis_events** — найденные события: `severity`/`title`/`description`
  — снэпшот на момент обнаружения (не меняется задним числом при правке
  правила), `evidence` (jsonb, например
  `{"message_ids": [9, 10], "gap_minutes": 47}`) — на что опирается вывод.

## Архитектура системы правил

```
App\Analysis\AnalysisRule    — интерфейс: key(), configSchema(), evaluate($dialog, $config)
App\Analysis\RuleRegistry    — 'key' → класс-обработчик, config/analysis_rules.php
App\Analysis\AnalysisRunner  — грузит enabled-правила из БД, резолвит класс, сохраняет
                                события; старые события диалога перед этим удаляет
App\Analysis\Rules\*         — сами правила
```

Правило — маленький класс без знания о контроллерах/HTTP/Eloquent: на вход
диалог с сообщениями и конфиг, на выход массив событий. `configSchema()`
описывает параметры (`{key, label, type, default}`), по нему фронтенд сам
строит форму редактирования — отдельная форма под каждое правило не нужна.

**Как расширять:** правку порога/критичности/текста/списка ключевых слов у
существующего правила и его включение/выключение делаем через БД (UI), код
не трогаем. Новый *тип* правила — один класс, реализующий `AnalysisRule`
(~20–40 строк), + строка в `config/analysis_rules.php` и в
`AnalysisRuleSeeder`; контроллеры, модели и `AnalysisRunner` не меняются.

Осознанно не делали generic-конструктор условий (JSON DSL/скриптинг) —
на объём задачи это оверинжиниринг и лишняя поверхность для ошибок
(валидация произвольных пользовательских выражений). Быстро настраиваемые
параметры через БД + быстро добавляемая логика через маленький класс —
более оправданный баланс.

Анализ запускается: (1) один раз при `db:seed` — сразу есть готовые события;
(2) вручную кнопкой «Повторить анализ» — синхронно, в текущем запросе, чтобы
сразу увидеть эффект от правки правила; (3) автоматически при новом
сообщении — `MessageObserver` ставит `AnalyzeDialogJob` в очередь
(`QUEUE_CONNECTION=database`), её разбирает контейнер `queue-worker`
(`--tries=3`). Ручная кнопка синхронна намеренно — explicit user action с
ожиданием немедленного результата; автопересчёт при потоке сообщений —
место, где синхронный анализ не масштабируется, поэтому он async.

## Правила анализа: обоснование и польза для бизнеса

| Правило | Что ищет | Критичность | Зачем бизнесу |
|---|---|---|---|
| **Долгий ответ менеджера** (`slow_response`) | Менеджер ответил клиенту позже порога (30 мин по умолчанию); от 2×порога — `high` | medium/high | Прямая метрика SLA: клиентов теряют не из-за качества ответа, а из-за задержки. Даёт конкретные случаи для разбора с менеджером, а не только усреднённую цифру. |
| **Клиент перестал отвечать** (`client_silence_after_manager`) | Последнее сообщение в диалоге — от менеджера, ответа не было | high | Прямой сигнал потерянного контакта — отличает диалоги, которые тихо «зависли», от явно закрытых. |
| **Возможное возражение клиента** (`possible_objection`) | Сообщение клиента содержит маркер возражения (настраиваемый список: «дорого», «подумаю», «конкурент» и т.п.) | low | Сырьё для базы знаний и обучения менеджеров: как реально звучат сомнения клиентов и как их отрабатывают — даже если сделка в итоге состоялась. |
| **Длинный диалог без продажи** (`long_effort_no_sale`) | Больше `min_messages` сообщений (10 по умолчанию), а результат не «купил» | medium | Много потраченного времени без сделки — приоритет для ручного разбора: либо процесс продажи неэффективен, либо лид некачественный. |

Правила выбирались так, чтобы покрыть разные измерения диалога — тайминг
(1), исход (2), содержание сообщений (3), агрегат «усилия vs результат» (4)
— а не дублировать одну эвристику под разными именами.

## Тестовые данные

`DialogSeeder` создаёт 9 диалогов с реалистичными сценариями (успешная
продажа, явный отказ, отработанное возражение с продажей, клиент перестал
отвечать после follow-up'ов, медленные ответы менеджера, длинный диалог без
результата, быстрые сделки, вежливый отказ «вернёмся позже») с управляемыми
интервалами между сообщениями — так, чтобы гарантированно срабатывало
каждое из 4 правил (проверено: 11 событий на 9 диалогов, каждое правило
минимум дважды). Диалоги распределены поровну по 3 на менеджера, чтобы
разграничение видимости по роли было заметно и при ручной проверке в
браузере: под менеджером — 3 диалога, под аналитиком — все 9.

## Приём внешних сообщений (стаб)

`POST /webhooks/{channel}` — вход для «живых» сообщений извне
(мессенджер-агрегатор вроде Wazzup/Chat2Desk, CRM), без сессии и
CSRF-токена (см. исключение в `bootstrap/app.php`) — аутентификация тут не
Laravel-мидлварь, а проверка подписи/секрета конкретного канала.

```
App\Ingestion\InboundChannelAdapter    — интерфейс: key(), verify($request), parse($payload)
App\Ingestion\ChannelAdapterRegistry   — 'channel' → класс-адаптер, config/inbound_channels.php
App\Ingestion\NormalizedInboundMessage — общий DTO, в который каждый адаптер приводит свой формат
App\Ingestion\Adapters\WazzupAdapter   — единственный пока адаптер (иллюстративный)
```

Тот же паттерн, что и у `AnalysisRule`/`RuleRegistry`: контроллер не знает
про вендоров, работает только с `NormalizedInboundMessage`. Новый канал —
новый класс `InboundChannelAdapter` + строка в конфиге.

Дальше — обычный `Dialog::firstOrCreate()` по `(source, external_thread_id)`
и `$dialog->messages()->create()` с уникальным `external_message_id`
(защита от повторной доставки). Это создание `Message`, поэтому
`MessageObserver` срабатывает как обычно — аналитика подключается без
единой правки в `AnalysisRunner` или правилах.

**Это стаб, не готовая интеграция**: `WazzupAdapter` приблизительно
воспроизводит форму реального вебхука Wazzup, чтобы показать контракт
адаптера, но не проверялся на живом аккаунте — перед подключением форму
payload нужно сверить с документацией вендора. `manager_id` берётся из
плоского конфига (один менеджер на канал); для нескольких номеров на
разных менеджеров потребуется таблица маппинга.

## Ограничения и что делать дальше

- Правила настраиваются через БД, но новый *тип* правила всё ещё требует
  деплоя кода (см. «Архитектура системы правил» — осознанный компромисс).
- `possible_objection` — substring-поиск по стемам слов, без морфологии/NLP;
  ключевое слово матчится с левой границей слова (regex с negative
  lookbehind), чтобы не срабатывать на «недорого» при ключевом «дорого» —
  но подбор суффиксов («подума» → «подумаю/подумать») намеренно открытый,
  это и есть поиск по стемам. Омонимы не решает — для продакшена стоит
  рассмотреть модель классификации текста.
- `slow_response` отличает ответ на сообщение клиента от исходящего
  follow-up менеджера после паузы: если сразу за закрывающим разрыв
  сообщением менеджера идёт ещё одно его сообщение без ответа клиента между
  ними, событие не создаётся (это уже не «долгий ответ», а повторное
  обращение к «отвалившемуся» клиенту — покрыто `client_silence_after_manager`).
  Единственный медленный ответ без последующего сообщения клиента
  по-прежнему считается `slow_response` — именно такие случаи прямее всего
  показывают потерю клиента из-за задержки.
